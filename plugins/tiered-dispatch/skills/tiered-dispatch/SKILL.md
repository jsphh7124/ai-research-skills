# Tiered Dispatch（分層派工）

你（協調者）不直接動手改程式碼，改由 Agent 工具依複雜度分派給不同模型執行，自己只負責拆解、指派與審核。

## 適用時機

多檔案、多子任務的程式修改工作，且子任務之間複雜度落差明顯（有需要深度判斷的部分，也有機械式重複的部分）。

不適用：單一小改動、探索性除錯、需要即時來回討論的任務（直接自己做，不要套流程徒增開銷）；子任務之間高度相依、共享大量脈絡的任務（每個子 agent 都得重新餵一遍脈絡，溝通成本會吃掉省下的額度）。

## 執行步驟

1. **拆解並分類。** 把任務拆成子任務清單，逐一標記複雜度，並寫下每個子任務獨立可驗證的完成條件：
   - **複雜**——需要理解架構、做設計取捨、除錯、跨檔案邏輯判斷 → `model: "opus"`
   - **機械式且零判斷**的批次操作（改名、格式轉換）→ `model: "haiku"`
   - **機械式但仍需基本上下文理解**的部分（套用既有 pattern、依範例覆寫到多個檔案）→ `model: "sonnet"`
   - **機械式、產出型、不需改檔**（摘要、文字轉換、批次判讀，輸出是一段可收回的文字）→ 可外派外部低成本 CLI agent（見下方「外部便宜派工」），不吃 Claude 額度

   標記不確定的子任務一律歸入「複雜」，不要為了省事下修。

2. **分派。** 用 Agent 工具指派，明確帶入檔案路徑、目標行為與步驟 1 定下的完成條件（子 agent 看不到這段對話，不要假設它記得任何脈絡）。分派給 Sonnet／Haiku 的 prompt 必須加一句：「若執行中發現需要設計取捨、跨檔案邏輯判斷或規格不明處，停下來回報現況，不要自行猜測補完」——回報後改派 Opus 或補充規格。彼此獨立的子任務在同一則回應中平行呼叫；有依賴關係的才序列執行。

3. **審核。** 每個 Agent 回傳後，逐項對照步驟 1 為該子任務定下的完成條件，親自讀 diff 逐條驗證，不能只信回傳摘要；任一條不滿足即不合格。不合格就指出具體問題重新指派，不要自己代勞改掉（除非只是微調級的收尾）。

4. **收尾。** 全部子任務通過審核後，若專案有測試就跑一次；改動夠大、或你不確定涵蓋是否周全時，收尾前做一次獨立複查（如 code review）。

## 外部便宜派工（選配）

若使用者本機裝有免費或低成本的外部 CLI agent（如 Gemini CLI、opencode 配免費模型），可把**產出型**子任務外派給它，完全不吃 Claude 額度。原則：

- 只派**產出型**子任務：外部 agent 回傳文字，你收回、對照完成條件驗證後自行落檔。**改檔案的子任務一律走 Agent 工具**——不要授予外部 agent 自主動檔案的權限（等於繞過本 session 的權限控管）。
- 以非互動模式呼叫（如 `gemini -p "{prompt}"` 或 `opencode run -m <model> "{prompt}" </dev/null`），檢查輸出成敗；失敗直接改派 haiku，不重試糾纏。
- 外部 agent 的配額與 Claude 額度**分池**，「省額度」是主要目的時優先考慮這一層。

## 注意事項

若使用者呼叫本 skill 的目的是省額度、而主 session 正使用高成本模型，開工前提醒使用者可先用 `/model` 切到較低成本的模型再繼續。
