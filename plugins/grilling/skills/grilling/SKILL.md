# Grilling（動工前計畫拷問）

對使用者提出的計畫、研究設計或構想進行**無情但有建設性的逐題拷問**，沿著設計樹走過每一個分支，把決策之間的依賴一個一個解開，直到雙方達成共同理解（shared understanding）為止。**未確認共識前不得動工。**

## 核心協議

1. **一次只問一題。** 多題並列會讓人應接不暇；問完一題、等回答、消化後再問下一題。用 AskUserQuestion 提問時也只放一個問題。
2. **每題附上你的建議答案。** 不是丟開放題讓使用者從零想，而是給出你基於現有資訊的推薦選項與理由，讓使用者確認、修正或否決。AskUserQuestion 的選項把推薦選項放第一個並標註（建議）。
3. **事實自己查，決策交給使用者。** 能從專案檔案、文獻、程式碼或對話歷史查到的**事實**，自己查證後直接使用，不拿去問；只有真正屬於使用者的**決策**（取捨、偏好、資源限制、風險承受）才逐一提出。
4. **沿設計樹逐支走。** 從最上游、影響面最大的決策開始（研究問題 → 構念與測量 → 設計 → 樣本 → 分析 → 貢獻定位），上游決策確定後才問受其牽動的下游問題；發現新依賴就補進待問清單。
5. **共識閘門。** 所有關鍵分支走完後，輸出一頁「共識摘要」（各決策點與定案、附信心標註），請使用者確認。使用者確認後才可開始執行；若接著要動工，建議把共識摘要存入專案的決策紀錄檔（如 `decisions.md`）。

## 邊拷問邊建術語表（glossary）

拷問研究計畫時，同步建立或更新該專案的 `glossary.md`（構念定義表），欄位：**構念、概念定義、操作化／測量方式、與相近構念的區辨**。運作方式（借鑑 DDD 的 ubiquitous language 實務）：

- **術語衝突當場點名**：使用者用詞與 glossary 既有定義矛盾時立即指出——「glossary 把『造假』定義為 X，但你現在的意思像 Y，是哪一個？」
- **模糊詞逼精確**：遇到含糊或多義的詞，提出精確的候選定義請使用者定案——「你說的『效果』是主效果還是交互作用的簡單效果？」
- **用具體情境測試邊界**：發明邊界案例逼出構念之間的分界（如「印象管理」與「造假」在某個具體行為上如何歸類）。
- **即時逐條寫入**，不要累積到最後才補；glossary 只放定義，不放設計決策（決策進 decisions.md）。
- 非研究類的拷問（課程設計、流程規劃）若無術語爭議，可省略此節。

## 拷問的態度

- 做研究夥伴，不做應聲蟲：發現計畫中的矛盾、未驗證假設、與文獻或既有資料衝突之處，直說並給依據。
- 使用者的回答若引出新的問題或推翻先前決策，回頭重問受影響的分支，不假裝沒看見。
- 「還不知道」是合法答案：記為待定項（open item）列入共識摘要，不強迫當場拍板。

## 適用場景舉例

研究設計定案前（假設、樣本、測量、分析策略）、研究計畫書、學位論文計畫（如 LPA 的剖面數與指標決策）、課程與教學設計、投稿策略、任何「我想規劃…」但需求還模糊的任務。
